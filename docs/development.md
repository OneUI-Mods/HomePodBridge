# Implementation

`HomePodRoutes` publishes `_raop._tcp` HomePod discoveries through `MediaRoute2ProviderService`. A route keeps a stable hashed device identity through name/address changes. Unsupported password-protected receivers and IPv6-only endpoints are omitted.

Apple Music's in-app chooser uses AndroidX. A framework route lacking the AndroidX descriptor extras is discarded before chooser filtering. The provider now includes the control-filter, device-type, playback-type, original-ID and extras fields understood by `MediaRouter2Utils`, along with the Cast-category features requested through discovery. This makes the existing AirPlay route visible in that chooser without loading code into the music app or implementing a Google Cast receiver. Direct chooser selections use the ordinary app-owned routing session; SystemUI-initiated transfers still use the manager path below. An experimental legacy provider was removed after confirming that the framework descriptor fixes the direct path.

`VectorModule` runs only in `com.android.systemui`. It adds this provider's routes to the system media route manager's lists, preserving existing routes. It does not modify any music application, media files, Google Cast SDK or system_server. ROM-specific differences still require device testing.

`SystemRouteTransfer` intercepts only this provider's transfers inside SystemUI. The UID-checked control provider asks `HomePodRoutes` to create an unsolicited session with `REQUEST_ID_NONE`. Android notifies route managers without handing that foreign-provider session to the source application's router, which otherwise immediately releases it. SystemUI receives its transfer callback after the sender acknowledges initial mute. Switching back to a system output releases the bridge session and the capture policy. Other providers retain the original framework path. Pending SystemUI transfers have a bounded failure timeout.

`SystemAudioBridge` uses the existing SystemUI CAPTURE_AUDIO_OUTPUT and MODIFY_AUDIO_ROUTING permissions. Its audio policy matches USAGE_MEDIA and the selected package's UID, with LOOP_BACK without RENDER. It does not override capture restrictions or open a microphone. A private PCM pipe transfers stereo signed 16-bit little-endian 44.1 kHz audio to the app. The system Binder accepts only the UID and signing certificate of the installed module. The expected public certificate is read from the loaded module archive. The registration provider accepts only the actual SystemUI UID. A rate-limited registration broadcast lets the app reacquire that Binder after process death without restarting SystemUI. Client death and closed pipes release recording and audio policies.

The user-requested whole-device mode instead creates a player mix with UID and voice-usage exclusions. It excludes this app and VOICE_COMMUNICATION / VOICE_COMMUNICATION_SIGNALLING, so playback and notification sounds across apps can be redirected without opening microphone or call sources. The selected-app mode retains its original UID + USAGE_MEDIA rules. Neither mode changes global capture permissions or opt-out flags. Standard MediaProjection fallback can capture media/game/unknown usages across apps in whole-device mode, with the platform's usual restrictions. Settings are private preferences and mode changes rebuild the owned capture policy; an existing route session is retained when possible so app choosers remain selected.

The capture service runs as a visible mediaPlayback foreground service in system mode. Standard MediaProjection is an optional fallback restricted to Apple Music. Projection consent is never cached for reuse. Streaming and capture use a serialized background worker; generation checks discard stale connection results. The app does not persist PCM or receiver credentials.

The JNI adapter feeds a bounded SPSC ring in the pinned Apache-2.0 sender. It enables strict SRP/receiver proof checks, uses HomePod transient pairing and runs the sender/network loop on its own thread. Receiver volume commands are queued to that thread. Failed handshakes never report a created route session.

The input reserve is configurable from 0–300 ms (default 150). While priming or recovering from starvation, the sender retains PCM and sends silence on the unchanged RTP timeline. It resumes after reaching the reserve rather than repeatedly consuming tiny fragments. A full native queue applies backpressure to the producer instead of dropping an unchecked write. Capture reads use configurable 2–40 ms blocks (default 10), always aligned to whole stereo frames. Presentation latency uses a configurable 10–2000 ms RTP timestamp offset (default 1500); it is a target, not an acoustic latency measurement or receiver guarantee. The native worker requests audio priority. A timed partial wake lock is renewed only during the active capture loop and released in finally, preventing foreground-service CPU suspend gaps without keeping the display on. Private diagnostics count queue depth, input shortages, buffering and backpressure; aggregate capture-frame / signal-block counts contain no recorded samples.

Every session starts at mute. The sender must receive the successful initial volume acknowledgement before reporting readiness or arming the audio pacer. The application always supports 0–100% in the UI, Java policy and native sender. The user's 5% constraint applies only to values the assistant sets while operating the physical device; it is not an application/build cap. The upstream sender resets a pre-start setVolume() and otherwise defaults to 0 dB, so configuring it before start was insufficient. Regression tests cover that failure, delayed or refused mute acknowledgement, bounded native volume policies and the application's full-range policy.

The app first tries Android's process-local Wi-Fi binding. When a forced VPN prevents that, the root helper owns a temporary route matching only this application's UID and the discovered receiver's private IPv4 address. It removes the exact rule on stop, helper termination or parent-process death. It does not change a VPN profile or other applications' routes. This fallback requires granting root access to HomePod Bridge.

The application uses Material Components 1.14.0 with a Material Design 3 day/night theme, dynamic colors, Material buttons/cards/dialogs and a Material volume slider.

The launcher uses a code-authored adaptive speaker/wireless icon with separate background, foreground and themed monochrome layers. The small white notification glyph is kept separate from the launcher icon.

HomePod transient authentication now derives the event-channel keys from the full SRP session key. The upstream path derived them only for pair-verify, silently discarded transient event requests and lost the receiver after roughly 30 seconds. The transient test now validates fragmented encrypted requests and the encrypted keep-alive reply.

## Audio profiles and compression

Material tabs separate connection/volume, audio scope/profiles/compression, and detailed tuning. Selected scope uses a check mark, filled color, bold text and a current-selection heading. The selected tab survives Activity recreation.

Low latency uses a default-on adaptive reserve starting at one 352-frame packet (about 8 ms), 2 ms capture blocks and a 50 ms receiver target; disabling adaptation restores a zero input reserve; custom tuning still exposes 10–2000 ms explicitly as experimental below 50 ms. High quality uses the existing lossless 44.1 kHz / signed 16-bit stereo path with a 150 ms reserve, 10 ms reads and a 1500 ms receiver target. These are mutually exclusive presets; switching both off restores retained custom values. Both preserve the same captured sample precision. High quality does not claim high-resolution capture, restore lossy source information, or increase the receiver's negotiated format. Lower target timestamps do not guarantee that HomePod honors that acoustic delay.

An independent, default-off lossless compression switch uses Apple's Apache-2.0 ALAC encoder, pinned in third_party/apple-alac/UPSTREAM.txt. It compresses each existing 352-frame packet in fast mode with no extra codec lookahead. The sample rate, bit depth, packet timeline, cipher and receiver format are unchanged. OFF uses the original uncompressed ALAC escape frames. Encoding failures or oversized output use that existing path. Reduced byte counts are content dependent; extra encoding work means compression is not a guarantee of lower delay. All profile, scope, codec and custom-buffer changes reconnect muted. Supported ABIs are little endian, explicitly configured for Apple's portable endian utilities.

Native regression tests round-trip 1200 packets of silence, tones, pseudorandom PCM, ramps and full-range samples through the encoder/decoder and require exact sample equality. The encrypted fake receiver checks compressed payloads and an opt-out back to uncompressed ALAC. Protocol timeline checks cover 10, 20 and 50 ms. Host encoder timing is diagnostic only, not a Galaxy benchmark or acoustic measurement.

Whole-device sharing owns an ordinary remote-volume MediaSession only while connected in that mode. Its absolute volume provider forwards buttons to the existing native command queue, synchronizes the displayed 0–100 value and releases on disconnect, mode change or service destruction. No music-app hook or global audio-capture policy change is involved. Foreground-app volume arbitration is platform dependent and requires physical verification.

## Frame pacing, direct capture and latency negotiation

RTP runs on absolute monotonic deadlines derived from 352-frame packets at 44.1 kHz (about 7.982 ms), rather than a repeating 8 ms timer. The audio clock starts after the mandatory initial mute ACK. A late wake may catch up at most 16 packets, then yields for one packet duration. Linux/Android waits use ppoll with nanosecond timeout precision; platforms with millisecond poll round upward. This fixes cumulative pacing drift without a busy loop or an unbounded recovery burst.

The root capture worker reads AudioRecord into a reused direct ByteBuffer and writes that buffer to the private pipe through FileChannel. The app reads into a reused direct buffer and JNI pushes its existing memory into the SPSC ring without a temporary short array/vector. The pipe and projection fallback require complete stereo frames. No captured PCM is written to disk. Native diagnostic counters are available through the capture service's protected dumpsys entrypoint.

Adaptive reserve is independently switchable and applies only to the low-latency preset. It increases by one packet on actual input starvation, capped at six packets (about 48 ms). After two seconds of exactly silent input it can return to one packet only by atomically discarding queued excess that contains exclusively zero-valued stereo frames. Any nonzero sample, including one-channel onsets, prevents that discard. Audible PCM is never removed to recover latency. Custom and high-quality reserves remain fixed.

AirPlay 2 stream SETUP advertises latencyMax equal to the configured frame target, and latencyMin equal to the smaller of that target and 250 ms. Valid positive integer receiver bounds up to ten seconds constrain the effective RTP/sync offset; missing values stay unknown and contradictory bounds are ignored together. One retry with the previous 250–2000 ms compatibility window is permitted for format/parameter refusals 400/406/415/451, before readiness or audio. Authentication refusals are never retried by this path. Repeated failure aborts. The requested value, effective send target, reported receiver minimum (or unknown), and compatibility fallback are shown separately. These protocol values are not measured acoustic delay.

Fake-receiver tests cover 10/20/50/1500 ms windows, reported lower/upper bounds, invalid/contradictory replies, bounded compatibility retries, authentication refusal and mute ordering. Frame-clock tests use irregular sub-millisecond wakes and a stalled consumer. Direct-buffer tests cover partial reads, endian layout, buffer reuse and incomplete stereo EOF. Whole-device volume verification includes foreground playback applications, compact volume controls, the three-dot expanded panel, relative keys and remote slider updates; screenshots and device-specific details remain in ignored research files.

The 10 ms experiment keeps the existing 352-frame ALAC packet format (about 7.982 ms) for receiver compatibility. A 2 ms capture read contains 88 stereo frames; with adaptive buffering OFF there is no additional configured sender reserve. The mixer/policy sink, kernel pipe, Wi-Fi transit, decoder and speaker may still add delay. This change does not claim a 10 ms measured acoustic path.

One UI's volume reducer normally leaves a dynamic row's icon action unchanged. The optional SystemUI reducer integration marks only the current lease's final row model as icon-clickable. Its owned icon action is handled once through the existing private volume callback, with a no-dispatch state preventing the ROM from issuing its unchanged value afterward. All callback IPC stays on the lease handler. The dynamic stream ID comes from the owned session map; no IPC occurs in the UI reducer callback. Other rows and connection lifetimes retain independent state, and reflection failures preserve the original state. Sound Assistant shares the default reducer through its wrapper. No plugin APK or application process is patched.

Sound Assistant can queue the unchanged remote value after the explicit icon callback. A per-session one-shot guard ignores only that previous value for 150 ms; a different value, expiry, or release consumes/clears the guard. This prevents the queued value from undoing mute while preserving subsequent slider commands. Protected diagnostics distinguish panel, route and private callback requests without recorded PCM.


## Silent low-latency preset regression

The 0.1.2 preset requested a 10 ms RTP lead and a matching constrained SETUP window. A successful SETUP and outgoing nonzero PCM did not prove audible receiver output. User listening confirmed 50 ms with 0 ms sender reserve and 2 ms capture, while 40 ms was silent; 10 ms was also silent with nonzero input. A separate 250 ms comparison initially had a paused source and was invalid, then passed after playback/input verification. The preset now uses 50 ms. Explicit custom targets below 50 ms remain available with an interoperability warning; this is an implementation-specific observed boundary, not a claimed HomePod hardware minimum or acoustic measurement. Mode changes still reconnect muted.

Protected handoff statistics measure the local monotonic interval from socket handoff until the RTP first sample's nominal presentation deadline, including encoding/packet-building cost. They count negative-deadline packets and report minimum/last lead. They do not measure radio transmission, receiver clock offset, decode/buffer delay, or acoustic latency. A 352-frame packet is paced at its final frame's deadline, consuming about 7.982 ms of the requested lead before network/receiver work. These statistics support separating sender lateness from receiver-side timing requirements without recording PCM.

During the first five seconds of a root capture connection, optional monotonic AudioRecord timestamps report the age of the latest frame read by the root worker. The calculation accounts for timestamp frame position versus cumulative read frames, using System.nanoTime with TIMEBASE_MONOTONIC. Unsupported timestamps and diagnostic exceptions do not affect capture. The value excludes the app-side pipe/ring, network and speaker and is not an acoustic measurement. No PCM is logged.

The connection tab includes an ordinary Material numeric volume input for a single exact 0–100 command, avoiding repeated key adjustments when an exact listening level is needed. It is enabled only while connected, validates the full application range, and does not impose an assistant-specific build limit.


### On-device follow-up for the 50 ms preset

The signed code-37 preset was installed and SystemUI reloaded through GalaxyReload. With adaptive reserve disabled, the UI and protected diagnostics both showed reserve 0 ms, capture reads 2 ms, and a 50 ms requested/effective target. Nonzero input was verified before the user confirmed audible output. The numeric volume dialog applied one explicit value correctly. Custom 40 ms remained selectable; both custom 40 and the restored preset reconnected muted. Playback was paused and sharing stopped after the checks.

At 50 ms, a live-input observation reported a 41.520 ms last local socket-handoff lead, a 36.884 ms session minimum and zero negative-lead packets. At custom 40 ms, the corresponding values were 31.749 ms, 28.373 ms and zero negative-lead packets over 657 measured packets, with nonzero audio input. The maximum observed encoder time in that 40 ms session was 372 microseconds. Neither session returned receiver minimum bounds or a numeric RECORD Audio-Latency header. These observations do not establish delivery over Wi-Fi, receiver clock accuracy, or audible rendering at 40 ms; the earlier user listening result for 40 ms was silent. The failure therefore is not explained by local handoff missing its nominal presentation deadline in these samples. Receiver scheduling, an effective receiver reserve, and clock mapping remain hypotheses.

AudioRecord timestamp-based latest-frame age was approximately 82–84 ms in both the silent-input and live-input sessions. This is an estimate from the policy sink's timestamp, not a loopback/acoustic measurement; vendor timestamp semantics and initial frame origin must be checked before treating it as a measured source-to-capture delay. AudioFlinger independently reported the remote-submix input and output at 44.1 kHz with 928-frame HAL periods (about 21.04 ms), a 2784-frame client recording allocation (about 63.13 ms), no FastMixer, no FastCapture and no available fast record track. Buffer capacity is not queue occupancy and must not be reported as an additive measured delay.

The AOSP [AudioPolicy sink implementation](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/media/java/android/media/audiopolicy/AudioPolicy.java) constructs its recording sink with AudioRecord.getMinBufferSize; the caller's smaller read block does not configure that underlying HAL period. The [remote-submix stream implementation](https://android.googlesource.com/platform/hardware/interfaces/+/refs/heads/main/audio/aidl/default/r_submix/StreamRemoteSubmix.cpp) also refines timestamps using pipe occupancy and reports a pipe-based latency estimate. These upstream implementations are references, not proof that the vendor HAL has identical timing semantics.

Further latency work must separate the Android capture path from receiver scheduling. A shorter ALAC/RTP packet than the current 352 frames could reduce approximately 8 ms of packet accumulation, but requires codec/protocol and receiver qualification. Altering RTP timestamp offsets to relabel the same acoustic delay is not an optimization. No Apple Music hook, system-server hook, global capture-policy change, microphone capture or vendor audio-server patch was introduced for this investigation. A 10 ms end-to-end path has not been achieved or measured.


## Live timing diagnostics and capture requests

The Diagnostics Material tab refreshes about every two seconds during a connection. It reports AudioRecord timestamp-derived latest-frame age as an estimate, blocking read duration, recording allocation capacity, paired system-to-app pipe transit, pipe write wait, queued PCM/reserve amounts, maximum ALAC encode time, packet duration, and local handoff lead/late counters. Wi-Fi one-way transit, receiver clock error, receiver processing and audible end-to-end delay remain explicitly unmeasured. Capacities, estimates and target/remaining times are not added into a fabricated total.

The signed, lifetime-bound SystemUI Binder protocol adds OPEN_TIMED and CAPTURE_TIMING. A timed PCM block has a 16-byte big-endian header (magic 0x48425031, positive aligned byte length, and System.nanoTime at completion of the matching AudioRecord read) followed by unchanged little-endian signed stereo PCM. A gather write reuses direct header/PCM buffers. The app validates bounds and rejects truncated or malformed framing before JNI. Transit is measured at completion of that exact payload read; it includes scheduling and pipe waits, and excludes audio acquisition before read completion. Legacy modules can still supply raw PCM via OPEN_CONFIGURED; timing remains unavailable. Unknown transaction fallback does not change route/capture authorization. CAPTURE_TIMING requires the same installed-module signing identity, UID and lifetime token as the capture channel.

Low latency requests a private, small FAST AudioRecord for the already registered mix only. It preserves the route address and fixed-volume capture attributes. Failure or initialization refusal releases the attempted recorder and falls back to the policy sink; a compatible policy-builder overload requests a smaller allocation, with the existing sink API as a final fallback. Successful construction is not proof of FAST admission, so the UI labels this as a request rather than accepted acceleration. AudioFlinger may internally increase buffer sizes or reject FAST; no audio-server, HAL or global system properties are modified. All paths retain the original UID/usage rules and cleanup on stop/client death. Capture/app/native sender threads request urgent-audio priority locally. MediaProjection capture now requests the source minimum rather than an unconditional extra 16 KiB/double-minimum allocation.

The user requested silence while sleeping. Subsequent qualification must keep the receiver muted and source playback stopped; successful transport or silence packets are not evidence of audible compatibility.


Timed capture drains complete stereo frames with READ_NON_BLOCKING up to the configured maximum block. When empty it blocks for one four-byte stereo frame, then drains the remainder through a reused direct-buffer slice. In contrast, a full-block blocking read can hold a residual part of a HAL burst until the next burst; 928 frames is not divisible by an 88-frame read. Timed framing carries each actual payload length, so short complete blocks can proceed immediately. Legacy raw-pipe sessions retain fixed blocking reads. Tests reconstruct multiple HAL-sized bursts exactly and verify that no blocking request in drain mode exceeds one frame. No busy polling, audible PCM discard, or additional PCM copy is introduced. Timing refresh has a separate observer notification so it never republishes routes, updates the volume lease, or rebuilds playback controls.

## Dedicated HAL inspection

The user authorized investigation and tuning of the Bridge-owned HAL route. Vector remains scoped to SystemUI; Apple Music, other routes, global capture policies and SELinux configuration remain untouched. Inspection alone does not change the HAL or establish a latency improvement.

An explicit activity dump request `--inspect-dedicated-hal N` (indices 0–2 only) starts a background, read-only root helper for three fixed audio implementation libraries. There is no caller-supplied path or command. Each read is limited to 16 MiB and 10 seconds; process streams are closed and the helper destroyed on all exits. Nothing runs automatically during app startup or capture. `--dedicated-hal-image` exports only the last inspected image through the existing DUMP-protected activity diagnostics; binary contents and root stderr are not written to logcat. The image is held in memory only. Private research copies must remain outside Git and source archives.

This is a capability investigation, not an active low-latency HAL backend. Route identity, object lifetime, writer quiescence and restoration must be established before any future live modification. Until then the shipped capture path retains its previous behavior.

The capture reply optionally appends the owned AudioMix registration after its file descriptor; older clients ignore the extension and new clients tolerate legacy replies. The value remains protected by module UID/certificate and the connection lifetime token. Closing the input clears the app's copy. An explicit `--inspect-dedicated-route` activity dump can run a bounded read-only root app_process probe; it accepts only that live registration (or no registration). It pins both HAL libraries by SHA256 before interpreting any implementation layout, checks the r_submix service UID/executable and module mappings, and follows the known route-map root rather than scanning heaps. Tree bounds, mapping bounds, string lengths, route reference count/format and MonoPipe vtable/capacity are checked. It opens process memory read-only and verifies repeated identity observations. Concurrent observations do not prove lifetime or writer quiescence and never authorize writes. No HAL hooks, injection, signals, suspension or memory writes are implemented. Reports stay in explicit DUMP-protected diagnostics, never route/UI state or logcat.

`--measure-capture` is an explicit DUMP-protected, bounded capture-only check for an idle bridge. It uses the existing UID/usage capture rules and normal timed PCM pipe, discards samples in memory, and never starts a network sender or source playback. It gathers unique fresh timestamp observations after warmup and requests read-only inspection with the registration returned for its own lifetime token. A 12-second watchdog closes its pipe/policy even if a read stalls; normal completion, exceptions and client death also clean up. `--capture-probe-status` reports the result without starting another check. Lock-screen authentication is neither dismissed nor modified.

Capture-only measurements with no active producer can report only about one HAL period even though the pipe retains its default target fill. These must not be compared to active-source measurements as an optimization. The explicit OPEN_SILENT_PROBE transaction therefore uses a dedicated SystemUI-owned USAGE_MEDIA AudioTrack whose only buffer is a newly allocated all-zero array. It accepts no caller-provided samples, starts only after the owned whole-device capture policy is registered, runs off the main thread and is stopped/released with that capture lifetime. Selected-app capture rules are not broadened; this probe refuses selected-app mode. It never starts Apple Music or a network sender. The timing extension includes aggregate zero-source written frames so a failed producer cannot be mistaken for a valid active-pipe benchmark. Normal OPEN/OPEN_TIMED sessions never create this source.


## Exclusive HAL access preflight (read only)

The separate explicit `--measure-capture-guard` benchmark adds a read-only native preflight after both library SHA256s and the live owned registration have been checked. The helper uses PTRACE_SEIZE/INTERRUPT (never SIGSTOP or EXITKILL), inventories/stops all service threads within a bounded attempt, and rechecks the exact route-map/object locks, reference count, format, MonoPipe identity and setter instructions. This briefly suspends service scheduling; it does not change any route's data or settings. It never attaches automatically or during normal playback. The ordinary helper always detaches, preserves unexpected pending signals and has a one-second fail-stop watchdog. Kernel detachment on tracer death is verified against synthetic child processes; no process is killed or restarted on the physical device. The target field is still read-only in this phase.

Tests run on an Android emulator against four threads in the test's own child. They verify actual stop/resume, queued signal delivery and resumed progress after the tracer itself is killed. Separate synthetic layout tests reject wrong registrations, locked maps/objects, extra input references, incompatible formats, wrong vtables, competing reserve values, shutdown pipes, cycles and mismatched setter instructions. ## Explicit dedicated-buffer comparison

After the read-only exclusion preflight passed on the pinned device, the explicit `--measure-capture-tuned` diagnostic can change the one verified owned MonoPipe target-fill field from 2587 to 1856 frames. Normal sharing still does not invoke this operation. It requires the 50 ms low-latency preset and existing whole-device capture rules. The helper stops the full service thread set for exclusion, rejects held map/object locks or changed route identity/format/refcount/vtable/instructions, writes one aligned 64-bit field, and verifies the complete surrounding 256-byte object region remained identical except for that field. A rejected, short or mismatched write is restored under the same exclusion. Unexpected independent state is not overwritten. Sample bytes, queue capacity, format, ordering and other routes are not modified.

The test uses zero-only input, no network sender and no music playback. It collects only unique fresh timestamp observations after the change is acknowledged and a further two-second settling period. #### Silent lifecycle fault verification

The protected commands `probe-hal-exit-fds`, `probe-hal-exit-map`, `probe-hal-exit-status` and `probe-hal-worker-hang` select a closed set of isolated-worker faults. They respectively exit after receiving duplicate FDs, exit after validating all mappings, exit immediately after dispatching one non-audio status command, or stop responding after mapping. The parent accepts an injected failure only when the expected checkpoint and exit code match; the hang case additionally requires an observed socket timeout and confirmed forced termination. The normal control case never accepts a failed worker as success. The status-dispatch fault cannot send start, burst, PCM or reserved-exit commands. The send guard refuses a missing notification word before writing to the command queue.

After each worker fault the Java supervisor still owns the original stream Binders/FDs and closes its streams and UUID-tagged resources. An exact baseline comparison, an empty route set and an unchanged HAL instance are required. These checks test isolated-worker death, not arbitrary death of the Java resource-owner process. Do not intentionally terminate that owner while it holds HAL streams until independent owner-death recovery is implemented.

`probe-hal-metrics` is a fixed read-only observation of the pinned idle module's process epoch, total FD count and total thread count. It does not expose FD targets or inspect unrelated stream objects. The totals include other audio activity, so changes alone cannot prove a Bridge leak; the ownership-scoped baseline comparison remains authoritative. Five repeated normal lifecycles passed before introducing these fault cases, with complete resource restoration and no HAL restart.

The hang test exposed that Android's forced process termination can close its stdout/stderr streams immediately. The supervisor now collects only available, bounded diagnostics before termination, confirms that the child exited, and then classifies the outcome. A hang requires the three-second read deadline, forced termination with exit code 137, and the matching checkpoint; early read errors or missing diagnostics cannot pass. Natural exits remain distinct even if observation is delayed. Regression tests emulate Android's pipe-closing behavior, early errors, missing pipes, natural exit and an unconfirmed kill.

A separate no-audio platform check found that this device's `Process.destroyForcibly()` returned exit code 143, and a 3000 ms local-socket read wait raised a generic `IOException` after about 3251 ms. The supervisor therefore uses its monotonic read deadline and explicitly sends SIGKILL only to the authenticated mapping worker. Before the FD handoff it records the peer's root UID, parent PID, process start time and exact nonce-bound command. All are rechecked immediately before signaling; changed identities, SystemUI, the HAL service and other commands are rejected. No PID or signal is accepted from a diagnostic caller.

The corrected signed candidate passed all four live worker faults with five interleaved normal controls. The hang case reached its read deadline at 3158 ms, confirmed worker exit 137, and returned to a working normal connection. Every case restored the exact port/configuration/patch baseline and left the route set empty. The HAL instance stayed unchanged, and observed total FD/thread counts stayed at 88/40 before and after every case. These are bounded lifecycle checks, not a sustained audio stress test or a latency improvement measurement; all streams remained unstarted with zero audio bytes.

### Dedicated policy input without an AudioRecord consumer

The virtual-pair worker passed 928-, 88-, 44- and 22-frame zero transfers, including a full input data/reply queue on worker exit and bounded backpressure when an output writer fills its private pipe. Do not retry with guessed Binder transactions, pretend to be AudioFlinger, or broaden capture/SELinux policy.

The replacement prototype registers a USAGE_MEDIA policy matching only its root process UID. The policy route connects and disconnects without creating an AudioRecord. The dedicated input borrows that registration's device port and records only newly returned configuration/patch IDs for cleanup; it never disconnects policy-owned ports directly. Open attempts are durably journaled before dispatch. An isolated native worker receives only the three input queues and reads 44 frames per burst. The optional producer is the existing fixed-zero AudioTrack source. The normal application backend remains unchanged.

The first 0.5-second comparisons found smaller mean pending-frame counts at 928 and 464 frames, but the 464 run logged short reads. Remote-submix reports requested input bytes and advances its frame counter even when it zero-pads missing data; successful replies and zero PCM alone cannot establish continuity. Those initial numbers must not be described as a successful latency improvement.

The input worker now queries position before each burst and waits until at least 44 frames are available. Only this sole, owned input reader uses that gate. It accepts only running/idle input states, validates every reply, bounds both command waits and availability waits, and drains data/replies before the next dispatch. Tests cover rejected states, negative positions, occupied queues and insufficient real-time throughput. Playback slowed by waiting must fail even if no short-read warning appears.

Tests cover linked profile defaults, independent persistence through other setting changes, reverting to linked timing, corrupt stored values, independent SETUP/SYNC/RTP values, PCM preservation, mute acknowledgement, receiver-response bounds and format/auth rejection handling.

Validation: 72 Java unit tests, release lint/build, license/APK checks and all three native codec/protocol/socket suites passed. The fake AP2 receiver verified advertised 50–50 ms with a 20 ms presentation offset, advertised 20–40 ms with a 50 ms offset, and 50–2000 ms with a 10 ms offset, including actual SYNC/RTP headers and lossless nonzero PCM round trips. On the physical Galaxy, command-only checks verified independent 50–80/20 ms settings, persistence across Bridge-only process restart, rejection of an inverted range without replacing the saved values, and restoration to linked 50/50/50 ms with the dedicated preference retained. The phone's Wi-Fi was off; discovery found no receiver, so no independent-timing HomePod handshake or audible playback result is claimed. The signed release was installed, no Wi-Fi setting was changed, and the device was left disconnected at volume0 with empty submix routes and no HAL owner.


### Notification-driven dedicated input and finer read validation

Dedicated input now waits on its validated FMQ NOT_EMPTY word with a bounded shared futex wait instead of sleeping for 100 us between reply checks. It clears only NOT_EMPTY, preserves NOT_FULL/unrelated bits, rechecks queue indices after clearing, tolerates EAGAIN/EINTR/spurious wakes and retains the original command deadline. A cached observable position from the sole-reader input reply avoids redundant getStatus commands while those known frames remain unread. No queue indices are reset, no producer settings are changed, and ownership/cleanup rules remain unchanged. The old polling loop is retained only in a closed diagnostic scenario for comparison.

A 22-frame (~0.499 ms) candidate uses bounded 112-byte live records (24-byte header plus 88 PCM bytes). The previous 44-frame live and zero-only formats remain separately validated. The initial app handshake reads a validated header and then the exact allowed payload. A fixed-clock live reader still supplies zero PCM while idle; it does not consume unavailable input. Closed zero-only HAL benchmarks compare the polling 44-frame, event-driven 44-frame and event-driven 22-frame paths at the same owned 800-frame reserve, checking real-time rate, complete payload, input shortfalls and resource restoration before accepting the candidate.

The buffer dialog now derives custom limits from the same constants as stored-setting validation. Preset values are read-only until an explicit switch to custom settings. Dedicated capture shows its fixed read unit instead of an ineffective 2–40 ms slider. Adaptive reserve cannot be replaced by an unused manual value inside the preset. Linked receiver timing is disabled while independent timing is active, and custom timing sliders accept 1 ms steps consistently with the validated values. These controls distinguish read unit, reserve, allocated HAL capacity and presentation settings; no unverified 50 ms receiver floor is imposed.


Device verification of the new wait primitive used only synthetic shared queues: the 200-reply polling trial had median/p95/mean 166/184/169 us, while the event trial had 21/27/22 us. These are shared-memory command round trips, not HAL capture or acoustic measurements. Two same-800-frame-reserve HAL comparisons then passed all 44-frame polling, 44-frame event/cached and 22-frame event/cached cases at 44,097–44,099 frames/second. The 44-frame polling input-command means were 827/746 us; 22-frame means were 482/497 us. Event-driven 44-frame reads averaged 994/996 us because the input itself paces capture; the entire synthetic IPC speedup must not be attributed to actual input reads. Cached status queries fell from 1,504/1,782 in the polling runs to 28/2 for event-driven 44-frame and 193/0 for 22-frame. The all-startup pending-frame averages did not improve consistently and do not establish a reduction in whole-device latency. Every case closed its streams and restored the exact inventories.

`probe-local-hal` now exercises the real root-host/socket/PcmPipe handoff without a receiver or network sender. It matches only the helper's root UID USAGE_MEDIA source, supplies fixed zeros, periodically stops/recreates that source, verifies each 22-frame payload and bounds the test at ten seconds. Two physical runs delivered 441,056 frames in approximately ten seconds, with median app transit 71/70 us and p95 169/171 us. Pending-frame means after 500 ms warmup were 490/487 (~11.1 ms), maxima 1,026/1,020 (~23.3 ms); these exclude idle records and are occupancy values, not frame age. Both confirmed cleanup. Force-stopping Bridge midway returned routes to empty in 2.34 seconds and a subsequent run succeeded, leaving no root owner. An additional 22-frame benchmark and ten-second local run recorded no remote-submix input-shortfall warnings. The phone remained off Wi-Fi, disconnected and at receiver volume0. HomePod output and nonzero live performance remain unverified. The remaining approximately 21 ms mixer production cadence was not modified; the 22-frame read unit does not remove it.

The local probe honors service cancellation and still allows its resource owner a bounded cleanup interval, clearing/restoring the Java interrupt flag around that wait. A startup failure with unconfirmed cleanup cannot be reported as a clean, unallocated session and blocks further capture in the app process.


### Opt-in partial ALAC packets and offline packet-assembly measurement

Tuning now offers Shorter audio packets as a default-off experiment. It is effective only with Low latency and active dedicated capture; standard capture, unsupported-backend fallback, high quality and classic RAOP retain 352-frame packets. AP2 can optionally transmit 88-frame (~1.995 ms) partial ALAC packets. The negotiated maximum/cookie/spf remain 352; the short compressed and uncompressed frames carry ALAC's explicit sample count. PCM precision and sample rate are unchanged. Frame pacing, RTP positions, sender byte accounting and diagnostic packet duration use the actual count. Packet size cannot be changed during a stream. The retransmit backlog expands from 1,024 to 4,096 entries in short mode to retain its approximately eight-second time span. Adaptive input reserve remains at its existing 8–48 ms budget; this experiment changes packet grouping independently of buffering and presentation offset. Mute acknowledgement remains mandatory before any audio packet.

Short packets increase packet frequency and have not been tested against HomePod. No automatic acoustic or below-50 ms success is claimed. The new preference survives unrelated source/profile/settings updates but defaults false and is inactive on backend fallback. The existing user-facing read-unit and buffer lower bounds remain unchanged.

`probe-packet-handoff` captures only the root helper's fixed-zero source through the existing dedicated HAL, local socket and PcmPipe. It compares four-second 352/88-frame grouping phases with the actual lossless encoder, measuring first HAL-read-completion to encoded-packet readiness after warmup. It does not open a receiver or network socket and cannot measure acoustic output or the complete source frame age. The native benchmark accepts only zero PCM and 88/352 frames, keeps its encoder under a mutex and releases it on stop; cancellation and uncertain HAL cleanup use the normal owner guards. Independent protocol tests decode partial/full compressed/uncompressed packets with the real Apple ALAC decoder, check 2 ms pacing, continuous RTP positions, delayed mute acknowledgement, retransmission beyond two seconds and unchanged classic-RAOP behavior.


Additional reserve candidates 752 and 768 are exposed only through fixed self-UID, zero-only diagnostic modes. Normal capture remains at the validated 800-frame target. Candidate transitions retain exact vendor hashes, route registration/refcount/format/vtable checks, stopped-thread exclusion, exact-field readback, rollback and restoration to 2587. Callers cannot supply an arbitrary target, route, package UID or memory address. Ten-second constant-source comparisons must check queue occupancy, actual HAL captured frame rate, inserted idle output and shortfall warnings before any candidate can become a production setting.
